# 頂尖作法提案（frontier-proposal-tw）

> 作者 **DavidY-tw**　│　AI 協作 Claude

目的：使用者問「這件事怎麼做到最好」時，不要直接動手，也不要只丟一句意見。先把限制與事實弄清楚，再給一份能直接拍板的提案；拍板後才實作。

## 何時用

- 使用者說：頂尖作法、最佳實務、業界怎麼做、你的看法、AI 最大潛能、做到最好、做得更美觀或更專業
- 使用者要一個「效果」但沒指定技術（例如「要有動態效果」「兩邊要統一」「手機也要方便看」）
- 一個決定會影響多個平台、多個 repo，或之後很難改

很小、做法只有一種的事（改字、修一個 bug）不用這個流程，直接做。

## 先選模式

| 模式 | 適用 | 走哪些步驟 |
|---|---|---|
| 輕量 | 呈現、UI、單一功能的效果（動態圖、儀表、排版） | 1 → 2 → 4 → 5 → 6 → 7 |
| 完整 | 系統架構、技術選型、PoC、要給主管或客戶拍板、牽涉資料品質或組織流程 | 1 → 2 → 3 → 4 → 5 → 6 → 7 |

- 判斷不了就用完整模式，但每段寫短。
- 使用者自己給了段落結構（例如「依序回答五段，不要跳段也不要合併」），照他的結構寫，本流程只當內容檢查表。

## 流程

### 1. 一句話重述目標，並檢查目標本身
寫出使用者真正要的結果與受眾，例如「GitHub 與 Obsidian 看到同一張會動的流程圖，手機也能看」。不確定就列 2～3 種理解，用選項問。

- 檢查目標是不是真正要的結果：例如「demo 證明 AI 找得回來」，真正要證明的是「找回的東西改變了決策或省下時間」。目標有問題就直接指出並給修正版，不要順著做。
- 寫出成功由誰判斷、在什麼場合（例如「主管看完 demo，願意開放真實資料」），以及對方最可能先問的問題（資料安全、誰維護、錯了誰負責）。

### 2. 查清限制與事實（表格）
每個相關平台或環境一列：能做什麼、不能做什麼、依據。

| 平台 | 能做 | 不能做 | 依據 |
|---|---|---|---|

- 能在本機查的就自己查（讀程式、跑指令、看版本、開瀏覽器試），不要叫使用者去查。
- 沒查證的寫「未驗證」，不要用常識猜。
- 平台功能、版本、授權、價格這類會變的事實，用網路搜尋查官方文件並附連結；查不到就標未驗證。
- 使用者已在用的工具（例如 Obsidian、Git、既有變更單或維修系統）也各列一列，寫明它在方案中負責哪一層、不負責什麼。
- 版本會變的事（例如某平台內建的函式庫版本）特別標出來，提案不要依賴它。

### 3. 事前驗屍（完整模式）
先不給方案。假設這件事 3 個月後被放棄，列出最可能的 3 個原因：

- 每個原因標類型：**技術／資料／組織流程**。後兩類一定要檢查，失敗多半不在技術。
- 寫成具體情境，例如「維修日誌只記做了什麼、沒記為什麼，召回的只是碎片」，不要寫「資料品質不佳」這種空話。
- 標出最可能致命的一個。第 5 步的推薦必須逐條回應這些原因。

### 4. 領域頂尖作法
**輕量模式**：5～7 條，每條一句做法＋一句為什麼，選和這件事真正相關的。常用的面向：

- **單一來源**：定義一次，各平台的輸出都由它產生，並用測試擋下不一致
- **有意義**：效果要傳達資訊（方向、狀態、真實資料），不是裝飾
- **靜止時就完整**：動畫、載入、腳本失效時內容仍然完整可讀
- **無障礙**：減少動態、替代文字、亮暗配色、手機寬度
- **新鮮度看得見**：快照標資料時間，由排程或指令自動重產，不靠手動
- **輕量與可維護**：選最小、最穩的技術，避免綁定會變的版本
- **分層**：摘要給一眼看懂，細節連到可互動的地方

**完整模式**：先抽象、再移植，避免只在本領域的舊做法裡打轉。

1. **結構抽象**：用一句話寫出問題的核心結構，不能出現本領域名詞和技術名詞（例如不准用「工程」「知識圖譜」「AI」），逼出可以跨領域比對的形狀。
2. **跨領域移植**：列 3～5 個已經把這個結構制度化的領域，每個寫四項：
   - 具體機制：流程步驟或資料欄位，不能只給名詞（要寫「Status: proposed／accepted／superseded＋取代連結」，不能只寫「用 ADR」）
   - 搬過來要改什麼
   - 類比在哪裡不成立（強制力、改動成本、權威層級、資料是否公開，常是斷點）
   - 沒查證的細節
3. 至少一個領域要是使用者所在產業的鄰近領域（例如水處理儀控 → 製程安全 MOC）。這類最容易直接接上既有制度。

### 5. 收斂：推薦方案
- 只推薦一個，寫清楚：做什麼、輸出在哪、怎麼保持同步、怎麼驗證。
- 使用者已經提的方向（例如「OWL＋Neo4j 或 DuckDB」）要明確評估；不推薦也要說為什麼。
- 完整模式要逐條對照第 3 步的失敗原因，寫出方案怎麼避開；避不開的寫成已知風險。
- 複雜系統先給 ASCII 架構圖或 Pydantic／DB schema，再寫文字。
- **驗收標準 3～5 條**：必須能自動驗證（指令、數字門檻、輸出檔案），格式沿用 spec-handoff-tw。
- **第一步**：2 天內做得完，而且先驗證最可能致命的失敗原因（常常是先手工做 10 筆，而不是先寫程式）。
- **改變推薦的條件**：寫 2～4 條「出現 X 就改走 Y」，替代方案放在這裡，不另開比較表。
- 輕量模式可以改列 1～2 個替代方案，各一句取捨（例如「最快但不會隨資料更新」）。
- 寫出花費（API 額度、真錢）、預估時間、風險；風險裡沒驗證過的標「未驗證」，並寫做完後怎麼驗證。

### 6. 讓使用者一鍵決定
- 用選項視窗（AskUserQuestion）或代號（A／B／C），推薦項放第一個並標「推薦」。
- 一次有多個決定就分題問，不要讓使用者打長文字。
- 使用者只要分析、已指定只要一個推薦時，不硬塞選項視窗；結尾用一行問要不要依 spec-handoff-tw 寫 spec。
- 碰到使用者規定「必須先問」的事（花錢、刪除、改全域設定、安裝技能或外掛、對外發布），在選項裡寫明。

### 7. 決定後交棒
- 小項目直接實作；大項目先依 spec-handoff-tw 寫 spec，再交給 autonomous-dev-loop。
- 實作完：自己驗證（含實際渲染或實際執行，不只跑單元測試）、交 code-reviewer 審查、修必修項目、證據寫進 02_data。
- 回報時分清「已實測」與「未驗證」，例如「瀏覽器實測正常，GitHub 頁面未驗證（私人 repo，瀏覽器沒登入）」。

## 輸出格式

```
## 結論
<推薦方案一句話＋為什麼>

## 先講限制
| 平台 | 能做 | 不能做 | 依據 |

## 頂尖作法
1. <做法>：<為什麼>
…

## 建議方案
- 做什麼／輸出在哪／怎麼同步／怎麼驗證
- 花費：…　時間：…
- 風險（未驗證）：…

<選項視窗或代號：A 推薦／B／C>
```

完整模式另加以下段落（放在「先講限制」之後；「建議方案」改寫成「收斂決策」）：

```
## 目的確認
<一句話複述；目標有問題直接指出>

## 事前驗屍
| # | 3 個月後被放棄的原因 | 類型（技術／資料／組織流程） |

## 結構抽象
> <一句話，不含本領域名詞與技術名詞>

## 跨領域移植
**<領域>**：機制／要改什麼／不成立處／未查證

## 收斂決策
<架構圖或 schema>
驗收標準（3～5 條，可自動驗證）
第一步（2 天內）
改變推薦的條件
```

## 守則

- 結論先講，細節在後；不要長篇比較所有可能。
- 診斷段不給方案：事前驗屍、結構抽象寫完之前不提技術選型，避免先射箭再畫靶。
- 不編造數字、版本或「業界都這樣做」；說不出依據就標未驗證。
- 推薦要落地：寫得出驗證方式才算推薦，寫不出的降為替代方案。
- 尊重已有的設計與規則：沿用專案現有的單一來源、色票、命名、證據格式。
- 做完後回顧一次：哪個假設錯了、下次提案要先查什麼，寫進該專案的 lessons 或記憶。

## 實例（agent-legion，2026-11-15）

使用者：「將 Obsidian 流程、儀表以動態效果呈現，GitHub README 也要同步支援動態效果，提出這類領域頂尖作法與看法」

- 限制：GitHub README 不執行 JavaScript；Obsidian 的 Canvas、Bases 沒有動畫；兩邊都能顯示「內含 CSS 動畫的 SVG 圖片」；GitHub 與 Obsidian 內建的 mermaid 是否支援連線動畫語法，版本無法確認，標為未驗證，不依賴。
- 推薦：從單一定義產生動態 SVG（連線流動＋重播真實任務 T-0022 的路徑＋KPI 卡），兩邊嵌入同一個檔案；替代方案：只做流程、或錄 GIF。
- 使用者選 A。實作後瀏覽器實測動畫時間窗；審查抓到「實線被 mermaid 樣式蓋掉不會流動」→ 修正並加測試。教訓：CSS 注入要放在原有樣式之後，並在瀏覽器量實際生效的樣式，不能只看原始碼。

## 實例（工程經驗召回 PoC，2026-11-18，完整模式）

使用者：「多年的設備故障、選型、配線、異常紀錄散在 Markdown、PDF、Git、維修日誌，要做 2 週 PoC 讓主管願意開放真實資料；考慮 OWL＋Neo4j，或 append-only 事件日誌＋DuckDB」

- 目的修正：demo 要證明「找回的經驗改變新案決策或省下時間」，不只是「AI 找得回來」；並先確認 PoC 能用哪些資料。
- 驗屍：資料（紀錄只記做了什麼，缺條件與結果，名稱不一致）、組織（沒有寫入端，資料停在 PoC 那天）、技術（本體太早固化、引用無法回溯）。
- 結構抽象：把散落、帶時間的「情境→決策→結果」紀錄，在相似新情境出現時連同出處與當時條件召回，並讓人判斷條件是否仍成立。
- 移植：軟體 ADR（Status／supersedes）、製程安全 MOC、醫療 SOAP＋M&M、法律 citator（是否被推翻）、航空 ASRS＋ATA 編碼。
- 推薦：append-only 事件日誌（ADR×SOAP 欄位）＋DuckDB＋本機 Ollama，不做 OWL／Neo4j。驗收包括引用雜湊 100% 可回溯、15 題黃金題 Recall@5 ≥ 0.7；第一步先手填 10 筆，看欄位填不填得出來。
- 改變條件：過半填不出條件與結果 → 改做寫入模板與補錄；多跳推理不足 → 先試遞迴 CTE 再上圖資料庫；需要多人寫入 → 改 PostgreSQL。
- 教訓：使用者接著問「Obsidian 的用途」，表示提案沒交代他已在用的工具放在哪一層。限制表要把使用者既有工具列進去。
