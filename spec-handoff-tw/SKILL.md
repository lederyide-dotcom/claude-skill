# 規劃與交接（Claude App → Claude Code）

目的：讓 使用者 只出現在「定目標」與「驗收 demo」兩個節點，中間由 Claude Code 自主完成。spec 寫得好不好，決定 Claude Code 能不能放手做。

## 何時使用
- 使用者 說：規劃、開新任務、寫 spec、交給 Claude Code、PoC、要做 demo
- 任務預估超過 30 分鐘，或會動到多個檔案、資料或 GPU
- 小任務（單一檔案、10 分鐘內）不用完整 spec，直接在對話中列 3 行「目標／驗收／限制」即可

## 步驟

### 1. 釐清需求（最多 5 題，已知的跳過）
只問會改變做法的問題，優先順序：
1. 成果給誰用、在什麼場合（主管 demo、客戶提案、作品集、自用）
2. 怎樣算成功（可量測的數字或可觀察的行為）
3. 哪些事 Claude 可以自己決定
4. 哪些事一定要先問（資料定義、刪檔、付費服務、對外介面）
5. 期限與硬體限制

上下文已經能回答的（例如 Q4 目標、既有專案背景）不要再問。

### 2. 可行性檢查
- 涉及本機模型、GPU、VRAM → 套用 local-ai-stack-win 估算（RTX 4060 8GB）
- 涉及已安裝工具、版本、路徑 → 套用 pc-dev-env-win，不建議重裝
- 新專案資料夾 → 套用 project-scaffold-tw 的命名與結構
- 做不到或風險高的，直接說，並給替代方案

### 3. 產出 spec.md（固定格式）

```markdown
# spec：<任務名稱>
版本：v0.1｜日期：YYYY-MM-DD｜repo：<repo 名稱>

## 最終目標（為什麼做）
<給誰用、用在什麼場合、成功是什麼樣子；1–3 句>

## 本次任務
<這一輪的具體範圍；條列>

## 不在範圍內
<明確排除的項目，避免 Claude Code 自行擴大>

## 驗收標準（必須能自動驗證）
- [ ] <指標>：<驗證指令>，結果寫入 02_data/<檔名>
- [ ] <行為>：<測試指令或 curl>
- [ ] 所有測試通過：`<測試指令>`
- [ ] 一鍵啟動可用：`<啟動指令>`

## 可以自行決定
<實作細節、套件選擇、超參數、檔案結構…>

## 必須停下來問我
<改動資料或類別定義、刪除原始資料、新增付費服務、改變對外 API、需要超過 8GB VRAM…>

## 環境與限制
<Windows 原生為主、Linux 需求走 WSL2/Docker、RTX 4060 8GB、相關服務埠、資料位置>

## 已知背景
<先前嘗試過的做法與失敗原因、參考資料>
```

### 4. 驗收標準撰寫規則
每一條都要能由 Claude Code 自己跑指令判定過或不過。

| ❌ 不可驗證 | ✅ 可驗證 |
|---|---|
| 效果良好 | val mAP50 ≥ 0.60，寫入 02_data/metrics.csv |
| 速度要快 | GPU 單張推論 < 50ms，跑 3 次取平均 |
| API 正常 | `curl localhost:8000/health` 回 200 |
| 資料切分正確 | pytest 驗證同一影片不同時出現在 train 與 val |
| 可以 demo | `docker compose up -d` 後 60 秒內首頁可開 |

門檻數字不確定時，標「暫定」並寫明依據，不要編造。

### 5. 交付
- 有 GitHub 連接器：直接寫入 repo 的 `03_docs/spec.md`（新分支或直接 commit，依 使用者 指示）
- 沒有：產出檔案讓 使用者 放進 repo
- 同時附上 Claude Code 開工提示：

```
讀 CLAUDE.md 與 03_docs/spec.md。
先用 plan mode 給我執行計畫：步驟、每步驗證方式、預估耗時、可能卡關處。
我確認後，在 spec「可以自行決定」範圍內放手執行到驗收標準全部通過，碰到「必須停下來問我」才停。
完成後呼叫 code-reviewer 審查、修正 🔴 項目，再依 autonomous-dev-loop 的格式回報。
```

## 檢查清單（交付前自查）
- 有「最終目標」，不只有任務
- 每條驗收標準都附驗證指令或檔案位置
- 「不在範圍內」與「必須問我」都有寫
- 硬體限制已核對 8GB VRAM
- 不確定的數字標「暫定」
