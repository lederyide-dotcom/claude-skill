# 自主開發迴圈

原則：完成 ≠ 寫完程式。完成 = 驗收標準全部親自驗證過，證據寫進檔案。使用者 不是輸送帶，不要把可以自己跑的驗證丟回給他。

## 0. 開工檢查（每次都做）
1. 讀根目錄 `CLAUDE.md` 與 `03_docs/spec.md`
   - 沒有 spec 且任務超過 30 分鐘 → 先依 spec-handoff-tw 產出草稿，請 使用者 確認
   - 小任務 → 在回覆中列 3 行「目標／驗收／限制」後直接做
2. `git status`：
   - 沒有 git → **停下**，提議 git init（沒有版本控制不放手做）
   - 有未 commit 的變更 → 先問 使用者 要 commit 還是 stash
3. 記下起點：`git rev-parse HEAD`，供審查時比對
4. 依任務類型組合其他 skill：
   - 指令、路徑、工具版本 → pc-dev-env-win
   - Ollama／vLLM／SD／Docker 服務／Bot webhook → local-ai-stack-win
   - 新增資料夾或檔案命名 → project-scaffold-tw

## 1. 計畫（plan mode）
輸出：步驟、每步驗證方式、預估耗時、風險與卡關點、會動到的檔案。
使用者 已說「直接做」或任務很小時可跳過確認，其餘等確認一次後就放手。

## 2. 執行規則
- 只在 spec「可以自行決定」的範圍內做決定；碰到「必須停下來問我」立即停
- 每完成一個驗收項目就 commit（訊息用繁體中文，說明做了什麼）
- 大改動或平行實驗 → 開分支或 worktree，不在 main 上試
- GPU 任務前先 `nvidia-smi`；同時只讓一個重 GPU 服務常駐（8GB VRAM）
- 長任務（超過 1 小時或跨 session）→ 持續更新 `03_docs/progress.md`：已完成、進行中、下一步、已知問題，讓新 session 能接手
- 新增套件立刻寫進 requirements.txt／pyproject.toml
- 機密只放 .env，絕不讀取或印出 .env 內容
- Windows 端指令用 `py -3.10` 或專案 venv，不假設 `python` 指向哪一版

## 3. 卡關規則
- 同一個錯誤修 3 次沒解 → 停下，整理：錯誤訊息、試過的做法、目前假設、需要 使用者 提供什麼
- 需要網路資源、帳號、付費服務或超過 8GB VRAM → 停下問
- 不要為了讓測試通過而修改測試或降低門檻；若認為門檻不合理，說明理由後問

## 4. 驗證（自己跑，不靠推測）
- 逐條執行 spec 的驗證指令，結果寫入 `02_data/`：
  - 數值指標 → `02_data/metrics.csv`（含日期、commit、指標、數值、指令）
  - 驗收紀錄 → `02_data/verify_YYYYMMDD.md`（每條標準：指令、輸出摘要、通過與否）
- 沒有實際跑過的結果，一律標「未驗證」，絕不編造數字或輸出
- 一鍵啟動指令要從乾淨狀態實測一次

## 5. 獨立審查
- 有 `code-reviewer` subagent → 呼叫它，傳入起點 commit 與 spec 路徑
- 沒有 → 以「沒看過實作過程」的角度自查：重跑驗證、看 `git diff <起點>`、檢查型別標註、例外處理、機密、寫死路徑、相依套件、資料洩漏
- 修正所有 🔴 必修項目後再交付；🟡 列在回報中讓 使用者 決定
- 重要節點（demo 前、對外交付）在回報中建議 使用者 另用 Codex 做第二意見

## 6. 回報格式（固定）

```markdown
## 結果：✅ 可交付／⚠️ 部分完成／❌ 未完成

### 驗收標準
| 項目 | 狀態 | 證據 |
|---|---|---|

### 變更
- 檔案：…（commit 範圍：<起點>..<HEAD>）

### 審查結果
- 🔴 已修：…
- 🟡 待決定：…

### 未完成／已知限制
- …

### 下一步建議
- 一項
```

成果要整理成文件、簡報、效能表或 demo 素材時，接著套用 demo-deliverable-pack。
